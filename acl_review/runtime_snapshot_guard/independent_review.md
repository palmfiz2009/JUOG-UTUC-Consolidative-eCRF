# Independent technical review: locked runtime snapshot check

Disposition: no blocking defect found in the reviewed fix for the stale pre-lock configuration/key snapshot race, provided all configuration/key mutations cooperate with the same project's ScriptLock. This is a technical code review and synthetic offline regression run, not formal QA, live old-key rejection proof, or deployment approval. No real services, credentials, deployments or live changes were accessed or performed by this review.

Reviewed build.py, both generated candidates and both minimal patches. The generated entry invokes juogRequireCurrentRuntimeSnapshot_ inside the acquired ScriptLock, before authenticated decode, spreadsheet open, ACL lookup or session writes. It reconstructs the same effective config plus three credential properties used by doPost. A stopped gate, changed execution stage, arbitrary config change or changed signing/resume/pepper key causes fixed CONFIGURATION_CHANGED rejection with lock release. No credential or config value is logged or returned. The existing early rejection checks may still reject a stale snapshot before lock acquisition, which is safe.

The final comparator recursively sorts object keys while retaining array order and scalar type. This removes the original JSON.stringify insertion-order false denial without weakening comparison for JSON-origin data. Both top-level and nested object reorder pass; array order, numeric/string differences and null-versus-missing fields remain distinct. This representation is intended for JSON-parsed configuration and string/null property values; it is not a general serializer for arbitrary functions, cyclic objects, undefined array entries or exotic objects. Those are not supplied by the normal doPost loader.

The correction is deliberately a single locked consistency check, not continuous authorization polling or automatic one-shot permission. For cooperating writers the lock prevents changes between the check and session/business operations. A disable or rotation that completed before the request acquires the lock is detected. If a request already holds the lock, a cooperating rotation/disable waits until that request finishes; rotation cannot retroactively cancel the in-flight operation. State changes must acquire this same script lock and retain it through all related property updates. A different Apps Script project has a different ScriptLock and cannot provide this guarantee.

A manual/noncooperating property writer can mutate after the comparison or between the sequential property reads. The independent test explicitly demonstrates that a gate change after comparison is not detected. Consequently this patch must not be described as protecting against concurrent manual property edits or atomic multi-property rotation without writer lock discipline. No same-lock rotation implementation was added by this change. This is an operational assumption, not a verified property of every external administrative path.

The patch does not change AUTH_CONNECT/business permissions, approved routes, schema parity, journal rows, recovery scope, session event schema or ACL. It does not prove old-key invalidation in a live environment; it only ensures a request's pre-lock effective key snapshot matches the current effective keys at the locked check. Both original bundles remain source inputs, and candidate manifests continue to state deployed=false.

## Independent verification

Command: node independent_tests.cjs

36 cases pass across version9_candidate.gs and recovery_candidate.gs. Tests execute the actual generated entry and snapshot helper in a Node VM, with synthetic config, synthetic credential strings and mocked Apps Script services. They exercise matching config, gate/stage/config changes, malformed/missing/null config, separate rotations of each key, object order normalization, array/type/null distinctions, property failures, lock acquisition failure and the noncooperating-writer limitation. Mocks assert all snapshot property reads occur while locked and all mismatches reject before decode/session/spreadsheet access. Both complete candidate bundles parse successfully in Node. Auth decode and session store are stubbed, so this test is not OIDC cryptographic verification, live key rotation validation or whole-system regression coverage.
