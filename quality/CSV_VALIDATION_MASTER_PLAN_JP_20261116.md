## 1. 目的と適用範囲
JUOG-UTUC01のStreamlit + Google Apps Script + Google Sheetsを、臨床研究の患者保護・データ完全性・記録の信頼性のリスクに見合うコンピュータ化システムとして設計、運用、検証可能にする。

対象業務：事前申請と中央MDT判定、正式登録と上限管理、術後30日/90日/6–24か月CRF、入力途中の仮保存、訂正・監査ログ、データ抽出/ロック、権限、バックアップ/復旧、設定・デプロイ・通知・画像受渡し。

適用法令の最終判断は試験区分（治験/特定臨床研究/その他の研究）と研究計画書・機関規程に基づきPI/法務・QAが確定する。本計画はICH E6(R3)に沿った**品質目標**であり、認証・適法性・正式GCP準拠の表明ではない。

## 2. 資産台帳と環境境界
1. **PRODUCTION**：現在の本番アプリ、GAS Web App deployment、Google Sheet。診療研究の実データが存在する可能性がある。未承認の検証書込・データ閲覧・資格情報取得・実メール送信を禁止。
2. **既存TEST**：過去のUAT資料が残る別環境。既存の架空/その他のデータを消去・再初期化しない。新候補の独立実機証拠とは区別。
3. **独立隔離QA**：専用の架空データ、固定したアプリSHA/GASバージョン/Sheets ID/ACL。独立QA承認を受けた限定試験だけを実施。通知・Dropbox等の外部到達は遮断する。
4. **GitHub offline**：コード静的検証/Node・Pythonの模擬統合/CIと文書。これは隔離実機OQの代替ではない。

各実機試験で、環境名、Git commit SHA、GAS script/deployment/version ID、対象Sheet ID、fixture ID（患者情報なし）、実行者ロール、日時とタイムゾーンを証拠へ固定する。

## 3. リスクに応じた要求・設計
- **P0: 個人情報・アクセス制御**：固有ユーザーID、施設別/役割別ACL、ログイン/失効/権限変更、情報露出抑制。AUTH-04正式FAILは未完のまま保持。
- **P0: CRF/監査完全性**：記録主体・操作時刻・訂正理由・変更前後、CRF/監査書込照合、送信ID一意性、障害後の同一要求復旧、重複/矛盾拒否。
- **P0: 臨床的安全性**：適格性、中央RECIST、研究計画書の時期制約、登録枠、30日→90日/FUP連携、臨床的な入力の妥当性。
- **P0: バックアップと変更管理**：復旧時の完全性、データ履歴の保全、コード/デプロイ構成の一致、承認付きリリース/ロールバック。
- **P1: 運用/データ搬出**：検証可能なエクスポート、画像匿名化、教育、SOP、データ固定/保存/廃棄。

要求仕様の初版：`quality/rtm/UAT67_BASELINE_20261116.json` 内の14 URS。1つのURSが複数の正式UATに対応する場合があり、逆もある。完全な設計要件ではないためQAが詳細FSを確定する。

## 4. CSVテスト戦略
- **IQ相当（設置・構成）**：アプリSHA、GASデプロイ、Sheet設定/アクセス/ロール、秘密値を記録しない構成台帳、バックアップ、環境の独立性を実測。
- **OQ相当（機能・例外）**：架空の本人・施設・ロールを使い、要求別の正常/異常/権限拒否/時刻境界/誤送信/切断/監査障害を計画した期待値と照合。
- **PQ/UAT相当（用途適合）**：責任者指定の研究フローを、研究計画書に適合する完全架空症例で、画面→GAS→記録→監査→表示/抽出までEnd-to-Endで検証。
- **Regression**：変更影響に限定した影響試験と、高リスク共通機能の必須回帰を実行。既存UAT67のPASS32は対象版での歴史的評価であり、新版の自動承認とはしない。
- **Security/Privacy**：入力値が画面、HTTP応答、実行ログ、Sheet、メール、添付ファイルへ漏れないことを確認（検査は権限と原本性を保護）。
- **Disaster recovery**：別復元先、権限分離、整合性、RPO/RTOの承認値、運用手順を実測。バックアップコピーの存在だけで復旧PASSとはしない。

## 5. 証拠の形式・トレーサビリティ
各テスト項目は以下の記録を持つ：
- URS ID → 機能仕様/設計（FS/DS） → リスク → 事前承認された試験手順 → fixture → 実測結果 → 原本（ハッシュ/リンク） → 逸脱・CAPA → 独立レビュアー → 承認日時。
- 環境/バージョン対応を明記。GitHub ActionsログやオフラインPASSは`TECHNICAL_ONLY`、架空実機の実測は`ISOLATED_LIVE_UNREVIEWED`、QA承認後のみ`FORMAL_ACCEPTED`とする。
- 無根拠なPASS変更、監査証跡の事後上書き、同一UUIDが不明なままの再送、患者識別子やtokenのGitHub添付を禁止。

## 6. Release gate（満たすまで本番適用不可）
A. 研究区分・適用要求、URS/FS/DSと高リスク設計がQA/責任者レビュー済み。  
B. 重大欠陥が0（または正式な逸脱/CAPA/科学的リスク受容により可と判断）。  
C. 実機の保存・監査・ロール拒否・復旧、主要臨床経路が計画どおり合格。  
D. 監査ログを含む原本証拠・環境同定・署名付きレビュー・RTMが完結。  
E. SOP/研修/アクセス付与/バックアップの継続運用準備が完了。  
F. PI・独立QA・データ管理者による正式な変更承認、デプロイ計画、復旧/ロールバック確認。  
G. 本番反映直後の読取専用検証・差異対応の手順が承認済み。

現時点ではA〜Gの全てを満たしたと宣言できない。正式UAT基準線は32 PASS/1 FAIL/29 BLOCKED/5 NOT RUN。
