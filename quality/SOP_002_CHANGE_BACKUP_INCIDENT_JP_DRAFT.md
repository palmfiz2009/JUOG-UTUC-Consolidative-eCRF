## 1. 変更管理（本番の承認なし反映を禁止）
1. Change Requestに目的、影響する画面/施設/臨床評価/監査・ACL、関連URS/リスク、対象ソースSHA、ロールバック計画を記録する。
2. 重大度と試験範囲を定義。特に個人情報、保存/監査、資格情報、適格性、登録枠、主要評価項目、凍結済みデータは最優先。
3. 隔離ブランチ→コードレビュー→構文/単体/模擬統合→独立隔離実機OQ/PQ→証拠照合→独立QAレビュー→PI承認の順に進める。
4. 本番反映前に正確なアプリSHA/GAS script+deployment ID/Sheet IDの組合せを固定し、保全とロールバックを実測/承認する。
5. 緊急変更時も原因、リスク、変更者、追加検証、事後承認を記録し、無記録の本番変更をしない。

## 2. バックアップと復旧
- バックアップ対象はCRF/Screening/Registry・監査・設定/ACL、正規アプリ/GASソースとデプロイ対応、復旧の手順・鍵管理。
- 頻度、RPO/RTO、保持期間、保存先・アクセス権・暗号化・オフサイト要否はPI/データ管理/QAが適用要件で決定する（ここで数値を勝手に承認しない）。
- バックアップの作成だけでPASSにしない。原本を変更せず別の隔離復元先に復元し、行数・ハッシュ・主要業務データ・監査ログ・変更履歴を確認する。
- 失敗/不整合は原本を保持して停止し、原因・再試験・CAPAを記録する。

## 3. 保存/訂正障害時
- 保存成功画面またはHTTP `ok:true` のみで保存成功とみなさず、CRFと監査行の一致を照合する。
- 通信切断や監査障害で結果が不明な場合、**既存UUID/要求を保持**して確認し、理由もなく別UUIDで再送しない。ブラウザ消失時の永続復旧は未実装なので専用障害手順に従う。
- 誤入力は新規症例番号を作らず、同じrecord_keyで「訂正報告」を行い、Versionと訂正理由を保持。元の履歴を消去しない。
- 既存データに識別子が疑われる場合、画面/ログ/外部共有を停止し、データ管理者・個人情報保護担当へ適切な経路で通知。未承認の削除・上書きをしない。

## 4. インシデント/CAPA
- 起点：個人情報/資格情報露出、誤デプロイ、他施設閲覧、監査不一致、保存欠落、復旧不能、統計解析に影響する変化。
- 記録：時刻/環境/版/機能/発見者/影響評価/拡大防止/根本原因/是正・予防措置/再試験/独立レビュー/完了判断。
- 重大性に応じた報告先・期限は、適用法令・病院/研究機関の規程に基づき正式決定する。
- 根本原因未確定での原状回復を「解決済み」としない。QAが効果確認後にCAPA終了判断する。

## 5. CSVを継続して維持
- 1回のUAT完了を終着点にしない。変更ごとのimpact assessmentと必要な再検証、教育、版記録を継続する。
- Release gate: 重大な未解決障害がない、URS/RTMと証拠が紐付く、実機OQ/PQが合格、SOP/教育準備、独立QAとPI承認。
- GitHub CIのPASSは上記の**技術的補助証拠**であり、正式UAT/CAPA/独立QAやGCP準拠を自動認定しない。
